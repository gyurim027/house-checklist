# 1. 기본 UX 원칙

본 서비스는 부동산 정보 탐색 서비스가 아니라 **현장에서 10분 안에 쓰는 기록 도구**다.

### 1.1 3버튼 세그먼트 중심

각 항목은 `짧은 문장 + [○ 양호][△ 문제][— 해당없음]` 세그먼트 컨트롤을 기본으로 한다. 긴 설명을 읽지 않아도 되게 한다.

### 1.2 한 손 사용

* 각 상태 버튼은 최소 44×44px 터치 영역.
* 항목 간 수직 간격 확보, 오탭 방지.
* 팝업·모달은 파괴적 동작(삭제, 기록 분리)에만 사용.

### 1.3 입력 부담 최소화

* 필수: **없음**. 저장 시점에 주소 또는 별칭 중 하나만 있으면 된다.
* 선택: 방문일/시간, 중개사·연락처, 보증금·매매가, 월세, 관리비, 각 항목 메모, 카테고리 메모.

### 1.4 자동 저장 중심

상태 변경은 즉시, 텍스트 입력은 500ms debounce 후 저장한다. 수동 `저장` 버튼도 함께 제공한다.

### 1.5 단계적 노출

핵심 31문항만 기본 노출하고, 선택 19문항은 카테고리별 `+ 더 볼 항목 N개` 버튼으로 펼친다. 펼침 여부는 기록에 저장한다.

# 2. 화면 구조

```text
[Header]

주소 검색 / 직접 입력
매물 별칭
기본 매물 정보

확인 현황 (확인율 — 무채색)

■ 건물 밖
   A. 건물·공용부
   B. 주차·주변환경·접근성

■ 건물 안
   C. 첫인상 (냄새·채광·환기)
   D. 벽·천장·창문
   E. 소음
   F. 주방
   G. 욕실·화장실
   H. 냉난방·전기
   I. 문·수납·공간

중개사에게 물어볼 것 (질문 목록 — 체크리스트 아님)

결과 (점수·등급 + 문제 항목 자동 요약)

최종 판단

저장 영역
```

대분류 2개(`건물 밖`, `건물 안`)는 시각적 구분선과 라벨로만 존재하며, 접기/펼치기 단위는 **세부 카테고리(A~I)** 다.

# 4. 매물 지정 — UI

## 4.1 주소 검색 UI 흐름

검색창에 키워드를 입력하면 검색 결과 리스트가 표시되고, 사용자가 하나를 선택하면 해당 주소가 선택된다. 검색창 아래에는 `주소를 직접 입력할게요` 진입점을 상시 노출해, 검색 실패·오프라인·API 미설정 상태에서도 점검을 시작할 수 있게 한다.

검색 실패 시 안내: `주소를 불러오지 못했습니다. 직접 입력해도 점검은 그대로 진행됩니다.`

검색 제공자, 도메인 등록, 서버 프록시 등 기술적 리스크와 폴백 설계는 [03_기술설계.md](./03_기술설계.md) §주소 검색 참고. 검색 결과와 직접 입력의 저장 형식도 해당 문서 참고.

## 4.2 매물 별칭 (신규 · 필수에 준함)

같은 건물의 다른 호수를 연달아 보는 경우 주소만으로는 기록을 구분할 수 없다.

* 라벨: `별칭`
* placeholder: `예: 302호 / 남향 투룸 / 3번째 집`
* 저장 목록과 결과 화면의 **1차 식별자**로 사용한다. 비어 있으면 `방문일 + 순번`으로 대체 표시한다.

## 4.3 주소 변경 UX — 항상 기존 체크 내용을 유지한다

주소 변경은 사용자의 점검 데이터를 엉뚱한 집의 기록으로 뒤바꿔버릴 수 있는, 되돌리기 어려운 조작이다. "새 기록으로 시작 / 주소만 수정" 두 갈래로 나누는 방식은 그 선택 자체가 사고 지점이 된다 — 오탭 한 번으로 A집 점검 내용이 B집 주소에 그대로 붙어버릴 수 있다.

**주소 변경은 언제나 "주소만 수정"으로만 동작한다.** 체크 상태·메모·결과는 그대로 유지되고 주소(및 필요하면 별칭)만 바뀐다. 선택을 강요하는 다이얼로그를 띄우지 않고, 변경 사실만 짧게 알린다.

```text
주소가 변경되었습니다.
지금까지 체크한 내용은 그대로 유지됩니다.

[확인]
```

* 이 화면에는 "새 기록 시작" 옵션을 두지 않는다. **다른 집을 새로 점검하려면 Empty State 또는 `새 집 체크하기`로 처음부터 새 기록을 만든다** ([03_기술설계.md](./03_기술설계.md) §목록·신규·삭제 참고).
* 새 기록 생성과 주소 수정을 서로 다른 진입점으로 완전히 분리함으로써, "주소 변경"이라는 단일 동작 안에 파괴적 분기가 존재하지 않게 한다.

## 4.4 기본 매물 정보 입력 폼

| 항목 | 타입 | 기본값 / placeholder |
|---|---|---|
| 방문일 | `<input type="date">` | 오늘 |
| 방문시간 | `<input type="time">` | 없음 |
| 중개사 / 연락처 | text | `예: OO부동산 / 010-0000-0000` |
| 보증금 / 매매가 | text | `예: 3억 5,000만 원` |
| 월세 | text | `예: 80만 원` |
| 관리비 | text | `예: 12만 원` |

금액은 형식을 강제하지 않는다. 통화 자동 계산도 제공하지 않는다.

# 6. 체크리스트 공통 컴포넌트

## 6.1 카테고리 카드

```text
▼ D. 벽·천장·창문                     응답 4/5 · 문제 1

   벽지·천장·창가에 검은 곰팡이가 없다.        [치명]
   [ ○ 양호 ][ △ 문제 ][ — 해당없음 ]

   천장이나 벽에 누런 물자국이 없다.           [치명]
   [ ○ 양호 ][ △ 문제 ][ — 해당없음 ]

   ...

   + 더 볼 항목 2개

   카테고리 메모
   [                                        ]
```

* 헤더 우측 요약은 `응답 n/m · 문제 k`. 문제 건수가 0이면 `· 문제 0`을 생략한다.
* 등급 배지(치명/중요/참고)는 문항 우측에 작게 표시하며, 배지 색은 **문제(△)로 표시된 경우에만** 채도를 갖는다.

## 6.2 접기 / 펼치기 (v1.0의 "이전/다음 이동" 폐지)

* 각 카테고리 헤더 전체가 토글 버튼이다.
* **카테고리 하단의 `[다음 · ○○ →]` 이동 버튼은 전면 삭제한다.** 스크롤 점프는 현장에서 현재 위치를 잃게 만들고, 접기/펼치기와 기능이 중복된다.
* 기본 상태: 첫 카테고리(A)만 펼침, 나머지 접힘.
* 카테고리를 모두 응답하면 자동으로 접지 **않는다**(사용자가 되돌아볼 수 있어야 한다).
* 접힘/펼침 상태는 기록에 저장한다.

## 6.3 상태 변경 동작

* ○ / △ / — 중 하나를 누르면 그 상태로 저장된다.
* **같은 버튼을 다시 누르면 미응답으로 되돌아간다.**
* △를 선택하면 해당 항목 아래에 메모 입력창이 자동으로 펼쳐진다(`무엇이 문제였나요?`). 다른 상태로 바꿔도 이미 쓴 메모는 지우지 않는다.
* 상태 변경 즉시 확인 현황·카테고리 요약·결과를 재계산한다.

# 7. 결과 화면 구성

```text
결과

    78점 · 보통
    치명적인 문제는 없지만 아쉬운 점이 있습니다.
    조건 협의 여지를 확인해 보세요.

    오늘 현장에서 눈으로 확인한 범위의 인상 점수입니다.
    시세·등기·계약 조건은 포함되지 않습니다.

    확인율 87% · 해당없음 3개 제외

문제로 표시한 항목 (5)

    [중요] 창틀과 벽 모서리에 물이 고였던 자국이나 들뜬 벽지가 없다.
           └ 안방 창틀 아래 벽지 들뜸
    [중요] 옆집이나 위층의 생활음이 들리지 않는다.
    [중요] 방마다 콘센트가 2구 이상 있다.
    [참고] 계단과 복도에 쓰레기나 개인 물건이 쌓여 있지 않다.
    [참고] 방문과 욕실문이 바닥에 끌리지 않고 여닫힌다.
```

# 8. 최종 판단 — UI 목업

## 8.1 단일 축 3지선다

```text
이 집, 어떻게 하시겠어요?

○ 계약 추진      — 이 집으로 진행하고 싶다
○ 보류           — 다른 집을 더 보고 결정한다
○ 탈락           — 이 집은 아니다
```

## 8.2 협의 필요 여부 (별도 체크)

```text
☐ 조건 협의가 필요하다 (가격 / 수리 / 입주일 등)
   [무엇을 협의할지 메모]
```

## 8.3 한 줄 평가

```text
placeholder: 이 집에 대한 느낌을 한 줄로 남겨보세요.
예: 채광과 위치는 좋지만 위층 발소리가 계속 들렸다.
```

개념 정의와 근거는 [01_체크리스트_정보구조.md](./01_체크리스트_정보구조.md) §최종 판단 참고.

# 9. 반응형 · UI 스타일

## 9.1 반응형

| 구간 | 처리 |
|---|---|
| Mobile 320~767px | 기준 화면. 모든 콘텐츠 1열. |
| Tablet / Desktop 768px+ | 중앙 배치, `max-width: 720px`. 체크리스트는 동일하게 1열 유지. |

## 9.2 색 사용 규칙 (가장 중요한 스타일 규칙)

**색은 오직 "결과"에만 쓴다.**

| 요소 | 색 |
|---|---|
| 확인율 바 · 카테고리 응답 수 | 무채색(회색 계열)만 |
| 미응답 항목 | 무채색, 테두리만 |
| 양호(○) 선택 상태 | 옅은 중립 톤 (초록으로 강조하지 않는다) |
| 문제(△) 선택 상태 | 경고색 + 좌측 세로 바 |
| 해당없음(—) 선택 상태 | 텍스트만 흐리게, 배경 없음 |
| 결과 점수·등급 | 초록 / 노랑 / 주황 / 빨강 |

* 양호를 초록으로 칠하면 "많이 체크할수록 좋은 집"이라는 v1.0의 오해가 그대로 재현되므로 금지한다.
* 항목 텍스트에 **취소선을 쓰지 않는다.** 응답 후에도 문장을 읽을 수 있어야 한다.
* 기본 디자인 방향: 밝은 배경, 높은 가독성, 카드 기반 카테고리 구분, 포인트 컬러 1개.

# 10. Empty State

```text
집 보러 가셨나요?

주소를 검색하고

```

저장된 기록이 있으면 하단에 `최근 체크한 집` 목록을 노출한다.

# 11. 완료 상태

별도 완료 화면으로 이동시키지 않는다. 페이지 하단에서 다음과 같이 표시한다.

```text
점검 기록 저장 완료

핵심 31개 중 29개 응답 (확인율 94%)
결과: 78점 · 보통

[체크 결과 복사]   [현재 내용 저장]
```

사용자는 언제든 위로 올라가 수정할 수 있다.
